# Local Production-v1 L2 — First Run and Managed Agent Protocol

## Authorized scope

- package one exact, versioned direct workspace-agent protocol;
- expose it through `forge agent protocol` without repository discovery or initialization;
- install the same exact bytes beside generated canonical context;
- reference its version, digest, and path from managed `AGENTS.md` and `CLAUDE.md` blocks;
- define document-first coverage, draft playback, exact owner confirmation, and bootstrap next
  action behavior; and
- preserve the existing byte-safe managed-marker and canonical-context boundaries.

## Contract and compatibility

Protocol `1.0.0` is an installed Markdown resource, not a governed record or new public data model.
It does not change the 51-model schema-`1.0` registry, journals, workflow locks, authorities,
transitions, pack formats, migrations, or archives. The protocol may be read before `forge init`.
Once canonical context is generated, exact protocol bytes are written to
`.forge/active/context/agent-protocol-1.0.0.md` and remain a regenerable tracked view.

Existing managed files containing the original marker span remain compatible. A preview replaces
only the bytes inside that span, while owner-authored prefix, suffix, newline convention, and file
identity remain subject to the existing compare-before-apply safety checks. Malformed markers,
symbolic links, irregular files, non-UTF-8 files, oversized output, and changes after preview remain
refusals.

The managed block binds both the canonical context digest and protocol digest. The protocol guides
conversation but grants no authority; canonical context continues to select the active governed
scope and legal worker actions.

## First-run behavior

The protocol requires the workspace agent to:

1. detect the installed CLI and protocol before repository-specific action;
2. distinguish uninitialized, initialized, active, unhealthy, and terminal-history states;
3. request and read owner-supplied documents before broad questioning;
4. play back coverage for vision, first-milestone definition of done, constraints, assets, labor
   split, and abandonment conditions;
5. ask only about material gaps and allow an explicitly bounded start with named uncertainty;
6. draft the vision, milestone objective, scope, exclusions, evidence, pack/workflow selection,
   explanation profile, and lineage;
7. present initialization and creation as separate owner decisions with exact commands and effects;
   and
8. validate the created repository, apply the provider-specific managed reference, read canonical
   context, and propose one FORGE-derived next action.

## Explicit exclusions

L2 does not implement transaction receipts, a scratchpad or recap, per-step mentoring fields,
operator-provenance records, new owner-action commands, rejection transitions, successor briefs,
candidate packaging, or final candidate validation. Those remain L3–L9 work.

It also does not automate an interview as a second state machine. The direct workspace agent
conducts the protocol conversationally, while FORGE supplies exact installed instructions,
governed state, and safe managed integration.

## Validation boundary

Focused validation proves repository-independent protocol access, exact installed bytes,
document-first coverage, managed Codex and Claude references, regeneration, byte preservation,
legacy marker refresh, and protocol-path safety. Repository-wide lint, typing, tests, version
consistency, and health checks must remain clean before L2 is handed to the owner.

Passing tests establish only L2 implementation evidence. The encompassing `implement` step remains
in progress through L7, and local Production-v1 acceptance remains reserved for later extended
owner testing.
